## ① 파이프라인 흐름

```
[수집]  collectors/ (coupang·naver·discovery) + modules/naver_open_api·youtube_api
          → reviews 테이블 (Supabase PostgreSQL)
[분석]  analyzers/review_analyzer.py → analysis_results 테이블
          (total_reviews_analyzed / pros_top5 / cons_top5 / recommended_for / not_recommended_for)
[생성]  generators/topic_generator.py     ← 주제 기반 단일 글 (본체)
        generators/top_n_generator.py     ← TOP N 비교 글 (topic_gen의 후처리 재사용)
        generators/auto_review_pipeline.py ← 키워드 한 줄 → 수집·분석·TOP N 자동 일괄
          Claude 호출 → _apply_grade_processing → _apply_buzz_polish → 이미지 삽입
          → content_drafts INSERT + drafts/*.md 저장
[발행]  publishers/hugo.py publish() → modules/product_verify.pre_publish_check (제품 판매상태만)
          → _convert_affiliate_links → _test_build → _git_push
        publishers/tistory.py (별도 경로)
[사후]  cli/full_audit.py — 전수 점검기. 발행 경로에 연결돼 있지 않음(수동 실행)
```

핵심: **생성기 내부 후처리(`_apply_buzz_polish`)가 품질의 실질 결정자**이고,
**발행 단계에는 본문 품질 게이트가 없다**(제품 단종/가격변동만 검사).

## ② Q1~Q6 답변

### Q1. 플레이스홀더가 왜 남는가 → 치환 실패가 아니라 "의도적 삭제"

- "일정 금액 / 가격대 / 쿠팡 현재가 기준"은 미치환 토큰이 **아니다**.
  `generators/topic_generator.py:713-741` `BUZZ_REPLACEMENTS`의 **금액제거·가격일반화 정규식**이
  Claude가 쓴 실제 숫자를 사후에 뭉갠 결과다.
  - `topic_generator.py:723` `(r"\d+[천만]?원\s*정도", "일정 금액")`
    → "kWh당 약 5천원 정도예요" → **"kWh당 약 일정 금액예요"** (보고된 22개 깨진 문장과 정확히 일치)
  - `topic_generator.py:737` `(r"\d+만원대", "가격대")`, `:740` 단독 `N만원` → "일정 가격"
- 입력 단계에서도 숫자를 막는다: `topic_generator.py:1146-1158` `_get_reference_data`가
  **current_price 숫자를 프롬프트에 아예 넣지 않고** `price_tier` 라벨만 전달.
- 프롬프트도 같은 방향: `topic_generator.py:405,416-418`(hybrid/realtime "가격 직접 숫자 표기 절대 금지"),
  `top_n_generator.py:161`.
- **치환 결과를 검사하는 장치는 부분적 뿐**: `topic_generator.py:745-753` "부작용정리" 규칙이
  이미 알려진 깨짐 6종만 사후 보정(주석에 "치환 결과를 검사하지 않아 어색한 문장을 만들었다"고 자인).
  조사·서술어가 이어지는 일반 케이스("~예요", "~입니다")는 보정 대상 밖.
- 발행을 막는 장치: **없음**. `publishers/hugo.py:90-115`는 제품 상태만 본다.

### Q2. 절단이 왜 생기는가 → max_tokens 초과, 그리고 아무도 확인하지 않음

- `topic_generator.py:40` / `top_n_generator.py:35` `MAX_TOKENS = 4096`.
  한국어는 토큰/글자 비가 높아 4096 토큰 ≈ 2,000~2,700자. 프롬프트 요구 분량은
  `topic_generator.py:598-599` "한글 1,500~2,500자" — 표·링크·front matter까지 합치면 상한에 닿는다.
  TOP 5 글(`top_n_generator.py:157-165`, 제품 5개 × 장단점 + 비교표 + 결론)은 구조적으로 초과 → **3위에서 종료**.
- `response.stop_reason`을 읽는 코드가 **레포 전체에 0건**(grep `stop_reason` 결과 없음).
  `topic_generator.py:244` / `top_n_generator.py:186`은 `resp.content[0].text`만 꺼내 그대로 다음 단계로 넘긴다.
- 출력 완결성(마지막 문장 종결·필수 섹션 존재·요구 순위 개수) 검사 코드 없음.
  타임아웃/후처리 오류는 원인이 아니다(후처리는 regex 치환뿐, 예외 시 상위로 전파).

### Q3. DB에 리뷰가 있는데 왜 "수백 건"인가 → 프롬프트가 그렇게 쓰라고 시킨다

- 주입 경로는 **있다**: `topic_generator.py:1163` `- 분석 리뷰 수: {total_reviews_analyzed}건`,
  `top_n_generator.py:195-200`은 합계까지 계산해 "순위 산정 기준" 박스에 실수치를 넣는다.
- 그런데 같은 프롬프트가 **뭉뚱그린 표현을 권장 문구로 제시**한다:
  `topic_generator.py:560` `- "수백 건의 후기를 분석해보면"` (근거 표현 다양화 예시 목록).
  후처리 `EVIDENCE_VARIANTS`(`:889-910`)도 `:905` "수백 건의 리뷰를 살펴보면"을 자동 삽입한다.
  → **프롬프트와 후처리 양쪽이 실수치를 모호어로 대체하도록 설계**돼 있다.
- 추가 누수 경로 2개:
  1. `topic_generator.py:204-215` — `content_class == "skeleton"`이면 제품·분석 데이터를 **통째로 제외**.
     이 글들은 근거로 쓸 숫자가 애초에 없다.
  2. `:1088-1100` — `products`를 `name/brand ILIKE %keyword%`로만 찾는다. 주제어가 제품명과
     안 겹치면 참고 데이터 0건 → "DB에서 관련 데이터를 찾지 못했습니다"만 찍고 **그대로 생성 진행**.

### Q4. 발행 전 게이트 → 사실상 없음

### Q5. 비추천·근거 블록을 어디에 넣어야 전 글에 적용되나

## ④ 우선순위 3가지

1. **발행 게이트 신설** (#4 + #9) — `publishers/hugo.py:90` 검증 블록에 본문 게이트 삽입.
   검사 4종: 미종결 문장 / `일정 금액·가격대` 잔존 / 필수 H2 누락 / 제목-본문 숫자 불일치.
   `cli/full_audit.py`의 B항목 검사 로직을 함수로 떼어 재사용하면 신규 코드가 가장 적다.
   이것만으로 결함 1·2·4·7의 **재발이 멈춘다**(기존 글은 별도 소급).
2. **금액 정책 반전** (#1 + #2) — `BUZZ_REPLACEMENTS`의 금액제거·가격일반화 9종 제거 +
   `_get_reference_data`가 실가격·검증일을 넘기도록 변경. 현행 "숫자 금지" 정책이
   결함 1·2를 **설계로 생산**하고 있으므로, 정책을 "숫자 + 기준일 병기"로 바꾸는 게 근치다.
3. **근거 실수치화** (#5 + #6 + #8) — `topic_generator.py:560`의 "수백 건" 예시 삭제,
   프롬프트 구조 템플릿에 비추천 H2 필수화, `_get_reference_data`에 리뷰 건수·평점·mention_rate·
   `not_recommended_for` 주입. 한 함수와 한 프롬프트 블록 수정으로 결함 3·4·5를 동시에 덮는다.

> 참고: `MAX_TOKENS` 상향(#3)은 1번 작업 전에 먼저 올려두는 게 좋다.
> 게이트를 먼저 켜면 절단 글이 전부 차단되어 발행이 멈춘다.
